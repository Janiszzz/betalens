# 独立下载与本地缓存预取（2026-11-04）

请求速度问题的直接原因是下载生成器与转换共用消费循环：生成器交出批组后，转换在途达到 6 个或写入队列堵塞，便不再推进下载调度。另一个原因是已完成但等待慢头部批组的结果仍占用网络预取名额。

## 已部署的改动

- 原始响应仍先保存为带 SHA 及元数据的 gzip JSON，再生成标准化 Parquet，之后根据固定意图和前后镜像写 PG/CH 并核验。各批次可以在这些阶段并行推进，不要求全部下载结束才入库。
- `DownloadBuffer` 用独立线程推进 HTTP 调度，向转换端只传批组编号和错误摘要；内存队列最多 1,024 个批组，不传响应正文。
- 网络侧同时预取最多 16 个未完成批组。已下载但被较早慢批组挡住的结果不占用该名额，后续请求继续推进；向转换、写入交付仍保留原顺序。
- 字节背压覆盖全部已下载但未消费的原始文件，包含尚未创建转换子任务的文件；共享归档按路径只计一次，全部使用者完成后释放预算，证据文件保留。
- 维持冻结的 8/4 GiB 高低水位和 10 GiB 最小剩余磁盘。触及高水位后完成已经开始的头部批组以避免互相等待，随后等待下游回落；在途响应可能使水位短暂超出。手动提交或失败目标导致积压无法回落时，保存检查点并明确暂停。
- 目录预热的独立过滤请求使用配置的下载并发。工作线程内部触发证券清单补取时保持同步获取，避免占满同一个线程池后再次等待该池。
- 本地停止传播到限频等待、重试等待及自定义适配器上下文；账户/接口限频、429 冷却、分页交叠、空页终点和 SHA 检查继续执行。
- 页面分开显示原始数据下载进度、待处理原始缓存与转换/写入进度；原有按任务总耗时计算的速度明确标为全程平均值（含缓存复用）。

三组件原有 CPU/内存预算保持：PG 3 核/14 GiB，CH 4 核/20 GiB，管理器 3.8 核/8 GiB。来源默认 12 个 HTTP 槽，实际请求继续服从冻结账户和接口额度。
