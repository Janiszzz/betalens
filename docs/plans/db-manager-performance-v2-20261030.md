## 2. 90% 资源预算与初始参数

采用 WSL 口径：12 个逻辑 CPU，`.wslconfig` 配置 48 GB，Linux 实际可见约 47 GiB。CPU 与内存分别计算，90% 是三个组件的合计预算。保持 WSL 配置，三者合计 CPU 配额 10.8 核、内存硬上限 42 GiB，分别约为可用 CPU 的 90%、内存的 89%；这些是上限，不要求持续占满。

| 组件 | CPU 硬配额 | 内存硬上限 | 应用内部预算 |
| --- | ---: | ---: | --- |
| PostgreSQL | 3.0 核 | 14 GiB | shared buffers 3.5 GiB；管理器最多 6 个 PG 活动连接。 |
| ClickHouse | 4.0 核 | 20 GiB | server tracked memory 15 GiB；单查询默认 4 GiB、只读审计 2 GiB；用户查询合计 10 GiB。 |
| 管理器进程树 | 3.8 核 | 8 GiB | 转换/校验共享 6 GiB，剩余空间供调度、缓存、Web 和状态库访问。 |
| 合计 | **10.8 核** | **42 GiB** | 约为 WSL 可用资源的 90%。 |

数据库通过 Compose `cpus`、`mem_limit` 落实；保持 `memswap_limit=mem_limit`。管理器使用宿主 systemd 服务，`CPUQuota=380%`、`MemoryHigh=7G`、`MemoryMax=8G`、`MemorySwapMax=0`，Web、worker、转换和校验子进程都在同一 cgroup。已确认宿主 systemd 正常运行。容器限制与应用预算配套生效，不能只靠线程数保证上限。Docker 的 CPU 配额及 memory/swap 语义依据[官方资源约束说明](https://docs.docker.com/engine/containers/resource_constraints/)。

## 3. 实施顺序

### P0：先停止并回退当前进行中的任务

1. 进入维护状态，拒绝新启动、续跑、人工提交；列出当时全部 queued/running 操作及其父任务。取消排队操作，对运行任务发出停止派发请求，等待网络请求结束及数据库安全边界落下；确认无在途写入、租约已结束后执行回退。
2. 记录停止时最后回执、目标范围、原始归档与镜像 SHA；备份控制库、配置和恢复清单。使用当前执行版本完成回退，期间保留现有容器资源，避免正在回退时降低内存导致再次失败。
3. 两库独立回退；同库按实际持久化顺序逆序处理，包括人工放行回执及失败/准备中的写入意图。多任务重叠时按实际写入先后逆序。参考域追加撤销事件，普通表恢复 before 镜像。
4. 若当前值已被后续任务修改、镜像缺失、哈希不符或无法判定部分写入，停止受影响范围并输出冲突；不覆盖后续数据，不用删除业务表替代回退。未解决冲突前不进入全面迁移。
5. 回退完成门槛：所有应回退范围恢复并核验、两库回退回执和审计同步完成、没有运行/排队操作。没有已应用数据的任务仅停止。默认范围为切换时进行中的任务，不追溯回退无关历史已完成任务。

### P1：移除旧执行模型，缩减控制面负担

- 新任务只能走 v2。普通表、手工表、CSV/XLSX/Parquet 文件、HTTP/Python 来源和三个参考域共用阶段调度；提取复用的映射、类型转换和参考域发布内核后，删除旧下载→预览→提交编排及基类回退分支。
- 旧 v1 任务仅保留列表、详情、审计、日志和导出。关闭续跑、提交、回退、重试、人工放行等写入口；禁用自动归档清理对旧证据的删除。历史事实与状态不改写成 v2 成功记录。
- v2 冻结合同按内容哈希保存一次；请求清单独立为按 task/request id 索引的行，批次保存合同引用及请求范围。子批次不再复制完整 plan/依赖清单，也不再作为完整用户任务反复初始化。
- 状态读取拆为摘要、单批、范围分页和显式完整导出。`check_cancel`、积压统计、分页查重、日志和任务进度使用窄查询；积压由事件增量维护，启动时一次校正。
- 增加按任务/批次/状态索引；日志增加 `(job,id)` 索引。短事务批量写入，归档和大 JSON 序列化在事务外完成。保持 SQLite WAL 与持久性要求，缓存连接按线程/进程隔离。
- 迁移先在控制库副本演练；核对任务、分片、回执、日志数量及哈希后切换。去重迁移后如需回收空间，在停机窗口采用 `VACUUM INTO` 新文件再校验切换；保留原库备份，不对运行库直接压缩。

### P2：下载、去重和转换形成连续流水线

- 一个任务级下载池覆盖所有就绪批组；同分页链的后继等待上一页，其他根请求和独立链可并发。按接口公平派发，冷却/重试放入延迟队列，不让睡眠线程占满全部 HTTP 工作槽。
- 一个账户/接口限速协调器统一预约请求，保留跨进程原子限频检查；减少每个线程轮询 SQLite 争抢。保持现有配额、429、权限错误和空页终止规则。
- 分页链按来源、参数范围、合同和规则版本建立增量行指纹索引；超内存时落独立索引文件。新页只比较新增指纹；恢复时验证原归档并重建一次。继续检测页内重复、跨页交叠、忽略 offset 和不完整分区。
- 来源合同、字段索引、日期过滤常量、映射转换计划按冻结版本编译一次。共享基础清单/日历只归档及标准化一次，通过引用供派生批次使用。
- 转换进程启动时初始化只需的只读上下文，避免每批构造完整管理服务；统一普通与派生转换入口，消除先转换再被基类结果替换的重复计算。
- Arrow RecordBatch/Parquet 扫描按行和字节双限制流式处理，避免全量 `to_pylist()`、重复构造 Arrow 表测大小和跨进程传大字典。同阶段的已核验输入复用；跨尝试及关键消费边界仍核验 SHA，不以文件名或 mtime 代替完整性证据。
- 独立批组转换完成即可进入可写队列；只有相关业务键、目标表范围或来源依赖形成顺序屏障。单库失败停止该库相关后继写入，另一库继续，积压超过水位时停止扩大下载。

### P3：有界入库、审计分级与参考域优化

- PG 使用进程内连接池，CH 使用线程隔离的持久 HTTP Session；来源 HTTP 也复用连接。连接和来源上下文不跨 spawn/fork 共享。结构检查按目标连接、冻结合同和 schema generation 复用，重新连接/DDL 变化后失效。
- 保留写前持久化意图、提交前竞争检查和写后全部受影响键/值核验。继续 PG COPY＋集合操作、CH Arrow 批量写入；把查询列/键/分区限制在所需范围。事件日期不在业务键时，仍查明真实分区，不能凭输入日期假定旧行位置。
- CH 对内存失败先确定执行阶段；只读查重可缩小键包重试，已产生写入意图后必须先协调实际状态，再按同一冻结意图恢复。不得简单重新调用 INSERT。核验 SQL 的 JOIN 构建侧保持有界，检查 EXPLAIN 与实际扫描/峰值内存。
- L0 保留状态、字段、行宽、日期/证券范围、分页完整性、类型/主键、镜像与存储一致性。L1 仅读取适用业务值列；L2 仅读取规则所需列和范围依赖；L3 才读取完整镜像、完整值及来源血缘。
- 校验先按表、证券、日期和批次元数据裁剪，再访问缓存和目标库；L1/L2 不加载不需要的 before/after 镜像。规则结果确定性合并，失败、未知、不适用和未执行含义保持不变。
- 独立批次进行有界并行读检查；CPU 规则使用共享进程槽。L3 来源重放仅对命中范围的子批次执行一次，双库共用来源证据；字段核验增量写报告明细，避免每批遍历累计证据。
- 校验运行记录规则版本、实际覆盖、任务与目标变更水位；开始/结束水位变化时标为过期。管理器对重叠写入范围协调检查，无关任务可同时下载。无法监控的外部直接改库不据缓存宣称已通过。
- 参考域按完整发布范围进入 v2 队列；相关来源证据齐备即可构建缓存。双库预览/核验/发布分别推进，保持各自锁和事件顺序。`heads/snapshot` 查询限定候选范围及其相关修订，保留相关修订的完整内容核验；不缓存整个历史为永久可信。
- 参考域 before 行按 scope 建索引，避免每个 scope 扫全部历史；原始/标准化样例流式截取，详细变化分页读取。继续遵守“先可信发布、再选最新完整范围”，不以关闭 L1–L3 绕过发布证据。
- 新 v2 回退合并相邻同表、无重叠键的逆操作；CH 对同一受影响分区尽量一次重建，逐原始批次记回执；重叠键保持严格逆序。覆盖统计从已写入批次收集受影响代码/范围，任务末尾合并刷新。

### P4：参数部署、监控与验收

- 在隔离环境完成新代码及 90% 配额组合验证后，一次性更新 Compose、PG/CH 配置及管理器 systemd 服务。保留原卷、路径、账号和凭据，重建容器不重建业务库；检查配置语法、实际生效值和健康状态。
- 指标分别记录 HTTP 等待/限频/归档、转换、排队、查重、镜像、写入、核验、审计同步与覆盖刷新耗时；显示 CPU、内存、I/O 压力、队列水位、PG 临时文件、CH 活跃 parts/合并积压及查询内存失败。
- 进度与日志接口只读轻量摘要，报告列表不返回全部报告内容；报告详情和样例真实分页、导出流式输出。维持冻结的请求/批次总数，分页后继不改变分母。
- 切换后历史停止/回退任务不自动恢复。仅显式新建并启动的 v2 任务执行；新增生产采集范围沿用现有显式启动机制。

## 4. 接口与兼容约定

- 创建请求省略 `pipeline_version` 时使用 2；显式传 1 返回 `422 legacy_pipeline_removed`，不默默改变旧请求的提交语义。
- 新任务继续支持 `auto_commit=false`：v2 先产生可核验缓存，用户显式提交。移除“使用旧管线”开关及旧 CLI 执行命令；统一使用 run/start、cancel、v2 commit、validate、rollback。
- 旧任务的变更 API/CLI 返回 `410 legacy_task_read_only`，附历史详情/导出入口；旧任务不自动迁移执行、不复用旧确认 token。业务参考域的查询、完整性与发布语义保持，执行入口改接 v2。
- 增加服务级 `resource_profile=throughput_90`，统一管理下载上限、CPU 进程槽、目标库查询额度及内存/积压水位；任务冻结所选配置和 resolved 参数。任务级覆盖只能降低额度，不能突破服务上限。
- 管线详情增加分阶段耗时、队列/资源指标；校验报告增加执行范围、已检查行数、规则版本和变更水位。报告明细单独分页存储，避免整个报告反复序列化到一个 ledger 值。
- 状态库结构升级保持迁移版本和恢复备份；不修改研究包 `betalens/`，不改变业务表主键、Decimal 精度、UTC 存储或参考域可信合同。

## 5. 测试、验收与回退条件

性能对照使用固定归档、本地 HTTP 来源和隔离 PG/CH，不重复消耗真实源端额度。分别比较当前配置、当前代码在 90% 预算下、新代码在 90% 预算下三组结果，区分代码收益和配额影响。每组至少三次取中位数，区分冷/热缓存；现有五日样本外增加 200 页长链、30 个交易日、多证券长历史、宽财报和完整参考域样本。

| 验收项 | 门槛 |
| --- | --- |
| 首步停止/回退 | 无在途写入及遗留队列；已应用范围恢复，失败/未知回执协调完毕；原始归档、镜像和历史可导出。 |
| 资源 | 持续混合负载 60 分钟；三组件 CPU 配额合计 ≤10.8、内存硬上限合计 ≤42 GiB；验证 WSL 可用内存低于 4 GiB 时的背压；无 OOM、无新增内存失败，合并和写入积压不持续上升。 |
| 分页复杂度 | 首次下载 200 页不再执行 19,900 次历史归档读取；每页最多一次历史索引重建读取，交叠/重复页检测结果相同。 |
| 控制面 | 8 万请求、5 万分片规模下，热缓存任务摘要 p95 ≤100 ms、最新日志 p95 ≤200 ms；这些接口不读完整计划、全部分片或镜像。 |
| 下载调度 | 有足够独立请求、无资源/配额冷却时，达到 `min(有效额度/60, 并发槽/响应延迟)` 的至少 90%；慢接口或单库失败不占满全部下载槽。 |
| 审计轻量化 | L1/L2 不执行无关完整镜像和来源重放；限定范围不扫描无关批次；所有必要检查与旧规则结果等价。 |
| 本地处理性能 | 相同 90% 预算下，代表性多表样本的转换＋写入＋审计中位数较当前代码缩短至少 30%，其余样本回归不超过 10%；未达标则保留剖析结果继续定位，不声称达成固定倍数。 |
| 数据一致性 | 两库按各自真实 before 值核对全部受影响键和值；fill_missing/refresh_source、空值、历史修订、时区、字段精度结果不变。 |
| 迁移与入口 | 所有新任务只能进入 v2；普通/文件/自定义来源/参考域均覆盖；旧任务变更入口稳定返回 410，查看/导出可用。 |

故障注入覆盖：归档完成未记账、意图持久化后未写、部分 CH 写入、写后未 ACK、单库失败、限频冷却、缓存篡改、SQLite 临时锁冲突、取消/重启、重叠键与后续修改、参考域发布/撤销、校验期间数据变化。报告顺序及通过/失败/未知结果必须与串行基准一致。

若配置无法启动、资源越界、出现数据差异或迁移校验失败，保持维护状态并恢复部署/配置快照；只有尚未产生新版写入时才可直接恢复旧控制库。已产生新版写入时，先按新版回执协调/回退，不能直接换回旧 SQLite 造成回执丢失。性能方案不包含关闭持久化、跳过键值核验或自动扩大来源额度。
