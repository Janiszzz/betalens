- 用户确认的归档、请求范围、结构版本、映射版本及目标 before 状态是固定提交前提。

## 3. 逐项设计与验收

### F01：固定用户确认的提交前提

1. 从预览生成不可变的提交记录，保存业务键、before/after 值及哈希、目标库、表和映射版本、归档摘要与提交记录版本。明确保存需要核验的全键清单，包括预览中跳过但参与确认的记录。
2. 提交接口接收该记录；检查目标状态时只能判定是否符合原前提，不能重新生成授权签名。
3. PG 在事务和现有表锁内复核原 before，再写入同一份 after；插入前提包含“该键不存在”。
4. 恢复逐行分类：仍为 before 的行可以继续；已经为 after 的行核验归属后补审计；其他值为冲突。恢复同样使用原前提。
5. CH 的检查到写入期间需要 B 批次定义的受控写入边界；不能声称一次查询加一次 INSERT 本身具备原子比较写入语义。

验收：分别在预览后、stage 后、恢复核验后插入并发修改。未经确认的新值不得被覆盖，审计 before 必须等于实际允许被覆盖的值。PG/CH 单目标以及双目标部分成功均需覆盖。

### F02：ClickHouse 回退的并发安全

第一步增加安全阻断：缺少可信写入隔离能力时，不进入当前整表 EXCHANGE 回退，返回明确的“需要受控维护窗口”，保留预览和审计。

完整回退流程采用受控维护窗口：

1. 所有管理器提交、回退和结构操作使用按目标库/表标识的共同写入协调机制，不能按各自状态目录分别加锁。
2. 部署侧限定可写账号及允许的写入入口，其他消费账号只读；进入维护窗口后停止接收新写入并等待已接受的写入完成。
3. 记录隔离能力和窗口状态。仅用户勾选一个“独占”选项，或只设置本机文件锁，都不能视为已证明隔离。
4. 隔离覆盖读取快照、重建、发布、核验和释放窗口的全流程。请求发出前持久化操作 ID、CH query ID、临时表、原表标识及发布检查点。HTTP 超时代表结果未知，先核实旧查询终止及交换是否发生，再允许后续写入。
5. 发布后核对键集合与内容，旧表在完成核验前保留；清理失败记录为可重试操作。

第一版写入隔离限定单实例写入服务和同步请求，不默认覆盖异步写入、Distributed 转发或跨主机自动接管。跨主机接管需实际隔离旧写者并排空请求，仅租约失效不能阻止旧进程继续执行 SQL。

CH 独立使用不依赖 PostgreSQL。需要修改数据库账号权限或增加跨主机协调能力的部署动作单独列出；若当前部署不能满足，自动回退及要求同键一致性保证的写入保持明确阻断，不能把这项计作“完整回退能力已恢复”。

验收：两个独立写者并发访问，包括不同状态目录的管理器。已成功接受的无关键 B 必须保留；维护窗口内新写入应被明确等待或拒绝。交换前后、核验前后中断均不得误删唯一可恢复的原表。最终验收包含真实隔离 CH，不能只依赖 SQL fake。

### F03：先核验 prepared 写入，再决定回退

1. 回退前枚举原任务所有目标和表的 prepared/completed 提交记录，不能只查询行审计。
2. 结合保存的 before/after 与当前目标识别仍为 before、已为 after、混合状态和后续冲突。当前等于 before 仅说明已经处于回退目标态，不能据此断言历史上从未写入。
3. 可证实的已写入变化先补齐持久化审计；只对实际写入且仍符合 after 的行生成逆操作。混合状态逐键登记已确认子集，不能调用旧 finish_commit 为整份意图生成审计。
4. 目标不可访问、提交记录与审计不一致、或无法唯一重建历史时进入 `needs_reconciliation`，保留具体范围。
5. 仅全部应回退变化完成且核验通过后，原任务才可进入 rolled_back；没有变化必须有“确实无写入”的证据。

验收：目标写入成功、finish_commit 抛异常、随即回退；恢复后原新增行应被删除，或任务明确阻断。不得再出现 rolled_back 但目标新增行仍在。

### F04：归档重放重新执行完整审计

1. 将阻断原因改为稳定代码，例如字段缺失、未知字段、请求范围不符、分页不完整和响应格式错误；中文提示只用于展示。
2. 下载、重放、预览和提交共用验证入口。重放校验 SHA、字段集合、必需字段、行宽、日期与证券范围以及分页/拆分完整性证据。
3. 保存原始请求事实；修改映射或补登记字段可以重审，但不能把原来的错误证券或不完整分页视为已修复。
4. 证券/日期角色从来源合同和映射读取，不能依赖本地字段恰好叫 `security_code`。
5. 旧任务缺少结构化原因或完整性证据时重新验证；无法证明完整的归档要求重新拉取。

验收：请求 A 返回 B、返回范围外日期、同键不同日期、截断分页、未知字段登记后重放等。正确补合同可以放行；请求范围和完整性错误持续阻断。

### F05：builtin 必须对应真实执行器

1. 建立内置处理器注册表，声明允许的本地表、源接口、输入依赖、输出字段及计算版本。
2. 规划、映射诊断、执行和字段审计使用同一注册解析结果，避免“诊断算已映射、执行却跳过”。
3. 自定义 direct 映射中的 builtin 规则只有存在合法处理器绑定时才可使用；其他情况报告具体字段错误。
4. 对已有内置 YAML 做确定性兼容归一化：旧文件可能没有 mapping_mode，不能简单按默认 direct 拒绝所有内置表。
5. 完成转换后核对声明输出是否存在；源端字段返回、成功转换和成功存储分别记录验证阶段。

验收：required=true 的 12.5 不得悄悄变成 null；合法后复权、指数原生值和行业展开继续通过。原有 29 个接口合同逐字段核查保持覆盖。

### F06：统一整数范围与物理类型

1. 统一逻辑 integer 为有符号 64 位，范围 `[-2^63, 2^63-1]`，PG 使用 bigint，CH 使用 Int64。
2. 转换、typed、文件导入和提交前共用范围校验；拒绝小数、NaN、Infinity 及越界值。
3. 延续现有超过 JavaScript 安全整数范围使用字符串的序列化，验证前端展示和回传没有精度损失。
4. 盘点既有 PG int32、CH Int32 以及相关控制表。生成显式扩大类型的迁移预览；物理类型版本纳入部署与确认核验。控制表刻意使用 int32 的内部计数列独立评估，不机械扩大全部列。
5. 尚未迁移的表按其实际范围审计，或阻止超范围任务提交，不能只更新逻辑合同便认为库内已经升级。

验收：测试 int32 两侧、int64 两侧及 JS 安全整数边界。合法 Int64 在迁移后两库往返一致，越界值在确认入库前被拒收。

### F07：可空性纳入结构生命周期

1. schema-plan、表清单漂移状态、安装和部署后核验共用同一结构比较逻辑，检查类型、精度、可空性及主键。
2. 可空改非空先统计并展示历史空值；存在空值时要求显式回填规则或阻断，不能填入猜测值。
3. 新增必填字段：空表可以直接建立约束；非空表采用“增列 → 审计回填 → 验证 → 加约束”的可恢复结构任务。
4. PG 生成正确的 NOT NULL/ALTER COLUMN 操作；CH 使用相应 Nullable 类型变更，并核对旧记录转换结果。
5. DDL 成功后重新读取实际结构，完全符合定义后再写入 ready 和部署版本。

验收：覆盖空表/非空表、历史空值、单库失败后重试、直接编辑 YAML、结构任务中断和对待提交任务的影响。

### F08：鉴权引用和脱敏统一处理

1. 定义显式鉴权描述：环境变量名、注入位置（header/query/body）及目标字段。持久化的是引用，真实值只在发请求时解析。
2. 普通 parameters 按端点参数合同校验。递归检查配置、绑定和任务参数，识别大小写、分隔符变化及嵌套敏感字段；关键字规则作为辅助，不能宣称可以识别任何任意命名的秘密。
3. 集中处理 sources.public、任务日志、错误信息、审计报告和导出；结合已解析的凭据值、已声明鉴权路径和敏感字段规则脱敏。
4. 脱敏后才进入持久化日志；请求记录固定业务参数和凭据引用，不能把实际凭据参与可公开的任务参数。
5. 扫描既有配置及任务中的已知敏感位置，报告文件和字段位置而不打印值；发现实际凭据时生成迁移到私有环境配置的方案。历史审计的清理需记录迁移，不能静默改写已确认哈希。
6. 原始 wire 若回显凭据，只能在私有目录受限保存；普通预览和导出必须脱敏，并区分原始归档与脱敏导出的哈希，不能借“原始响应”绕过公开输出限制。

验收：apiKey/apikey/access_key、嵌套对象与列表、query/body/header、错误回显与导出使用合成凭据测试；业务参数正常保留，凭据只在模拟源端收到。

### F09：快照参数保持统一的合并规则

按“端点合同默认值 → 表映射绑定值 → 本次任务值”合并，后者覆盖前者。快照、日频、区间请求共用该结果；是否附加日期参数单独由端点能力决定。

预览展示最终业务请求参数及本地过滤范围，实际下载使用同一份固定参数。通过缺省判断处理覆盖，保留显式的 0、false 等有效值。已有任务保持冻结请求，新规则通过关联新任务生效，不能在恢复时重新解释旧请求。

验收：合同 exchange=SSE、任务 exchange=SZSE/limit=7 时，编译结果和模拟 HTTP 收到的值均为 SZSE/7；绑定独有参数仍保留，快照不自动附加不支持的日期参数。

### F10/F11：审计同步形成持久化可重试流程

1. 在现有 SQLite 中记录控制表同步待办，包含目标、任务、记录类型、版本/序号、幂等键、最后错误及重试状态。
2. 本地业务状态变化与对应同步待办尽可能在同一 SQLite 事务中登记；待办确认发送前不能消失。
3. 数据状态和审计同步状态分开记录。页面显示“数据已写入、审计待同步”，完整完成态只在两者核验通过后展示。
4. 已完成任务的再次提交、已完成回退的重试仍处理同步待办，但不重复业务写入或逆操作。
5. 回退源任务与 rollback_task_id 的记录分别同步；旧状态不得在重试时覆盖更新状态。行审计使用稳定幂等标识。
6. 对旧任务提供只补控制表的核验/同步操作；无法重建的历史 before 值标为待核验，不能猜测补造。

验收：只让最后一次 import_task 同步失败、只让回退 import_row_audit 同步失败、重启服务后重试、两目标分别失败、重复发送及旧状态晚到。错误必须持久化，最终状态收敛，业务变化只执行一次。
